# The Cursor cross-check prompt

Paste everything below the line into Cursor (Agent mode) with the repository open.

---

You are an independent, adversarial reviewer AND fixer for `halvard`, a Python reference implementation of a corporate security product (eight phases, standard library only, Python 3.11+). The author of the code also wrote its tests and its evidence files, so do NOT trust them. Work in this order and do not skip steps.

**0. Orient (read only).** Read `README.md`, `docs/12-crosscheck-guide.md` (claims per phase, the author's own list of bug-prone areas 1 to 34, known gaps), `docs/04-threat-model.md`, and each phase's "Not demonstrated" section in the evidence files (`docs/07`, `09`, `11`, `14`, `16`, `18`, `20`, `22`). Note the hard rules: never brand with EPS/EPP/EDR/XDR/SIEM/SOAR; not an offensive tool; no document contents, keystrokes, webcam or microphone collected by default; do not invent metrics; show confidence and evidence where a detection is uncertain; every feature needs a customer-visible behaviour, an authorization rule, an audit record, and a test that fails if the behaviour is removed.

**1. Establish a baseline.** Create a branch `crosscheck`. Run `python3 -W ignore -m unittest discover -s tests` (on Windows: `py -W ignore -m unittest discover -s tests`). Expect everything to pass (a few Linux-only tests skip). Record the count. If anything fails, that is finding number one. Run each story and read its output critically: `python3 -m halvard.cli demo | setup | stolen-session | mailed-attachment | exposed-bucket | data-leak | patch-day | ai-agent | tripwires | rogue-device | platform` with `PYTHONPATH=src`.

**2. Falsify claims.** For each phase, take five claims from its evidence file and try to break them with a NEW test the author did not write (new inputs, odd orderings, boundary values, hostile strings, forged identities, expired or replayed items, two tenants at once). Put new tests in `tests/test_crosscheck_*.py`. A claim you cannot break is recorded as "held".

**3. Review the code for what tests cannot see.** Read with these questions: where can an unauthorized caller reach something (authorization bypass, a check on one path but not another, a check repeated in two places that can drift)? where can one tenant touch another? where can personal data reach a public audit field or a log? where does the code claim more than it does (docstrings, messages, docs versus behaviour)? where is a race, a time-of-check/time-of-use gap, an unbounded loop or memory growth, a swallowed exception that fails open, a default that is unsafe? Start with: `relay/actions.py`, `relay/authority.py`, `relay/commands.py`, `ledger/audit.py`, `tenancy.py`, `fabric/platform.py`, `fabric/keeper.py`, `fabric/delegation.py`, `fabric/crypto.py` (review the key hierarchy and lock behaviour, not the reference cipher as cryptography), `ward/agent.py` (`tripwire_gate`, `check_egress`, `execute_command`), `relay/journal.py`, `lumen/gateway.py`, `glass/service.py`, `glass/board.py`, `hearth/service.py`, `harbor/service.py`, `signet/detectors.py`, `courier/*`, `vaultline/*`, `atlas/*`.

**4. Check the tests themselves.** For ten tests of your choice, remove or break the behaviour they claim to cover (or run `python3 tools/mutation_check.py "<name filter>"`) and confirm they fail for the right reason. List any test that passes whatever the code does.

**5. Check the claims in prose.** List every sentence in `docs/` and in user-facing messages that states something the code does not do or no test proves, and every number shown to a user that is not computed from measured data.

**6. REPORT FIRST.** Before changing any source file, write `docs/crosscheck-report.md` with findings ranked Critical / High / Medium / Low. Each finding needs: a title, the file and line, what is wrong in one sentence, a failing test or a concrete input that proves it, and whether it is a code bug, a test gap, a documentation overclaim, or a design limit. Also list what you tried and could not break. Commit the report and the new failing tests together. Then STOP and print a short summary so I can read it before you fix anything.

**7. FIX (only after I reply "go").** For each finding, in severity order, one commit each: (a) the failing test already exists; (b) make the smallest change that fixes the cause (not the symptom); (c) run the whole suite; (d) never weaken, delete or skip an existing test to get green, and never edit an expected value to match new behaviour unless the old expectation was itself wrong, in which case explain why in the commit message; (e) if the fix changes documented behaviour, update the doc in the same commit; (f) if a finding is a design limit rather than a bug, add it to the "Known gaps" section instead of hiding it. Keep the standard library only. Keep Windows and Linux both working (use `os.path`/`pathlib`, UTF-8 for every text file, no hard-coded `/` separators in logic). After the fixes run the suite on a clean checkout and the full mutation sweep (`python3 tools/mutation_check.py`, long) and report how many mutants survive; any survivor needs a new test.

**8. Final report.** Update `docs/crosscheck-report.md` with what was fixed (commit ids), what was not and why, the final test count, and the mutation result. Do not claim anything you did not run.

Rules for you throughout: show evidence for every claim; say "I did not verify" when you did not; do not invent metrics; prefer fewer, well-proved findings over many speculative ones, and mark any uncertain one as "unconfirmed".
